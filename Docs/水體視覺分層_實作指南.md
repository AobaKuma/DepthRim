# 水體視覺分層：實作指南

本文件是 [水體視覺分層_計畫.md](水體視覺分層_計畫.md) 的實作版本：逐階段列出要改的檔案、資料格式、參數初始值、完成指標與驗收方式。計畫的方向（§7 已確認事項）不在這裡重述。

---

## 0. 共用約定

### 0.1 名詞

| 名詞 | 指的是 |
|---|---|
| 外海層 | `SectionLayer_WaterOuter` + `DepthRim_WaterOuter.frag.glsl`。繪製順序 3177，畫在迷霧之上、光照暗化之前 |
| 艙室層 | `SectionLayer_WaterVolume` + `DepthRim_WaterVolume.frag.glsl`。畫在 MoteLow 高度，只畫密閉艙室裡的積水 |
| 光照值 | 頂點周圍四格 `GlowGrid.VisualGlowAt` 的平均亮度，0–1 |
| 混濁度 | 著色器依光照值算出的覆蓋程度（alpha） |
| 層級 | `DepthTier`：淺海、變溫層、深海、深海海床 |

### 0.2 繪製順序（不可更動的相對位置）

| 繪製順序 | 內容 | 擁有者 |
|---|---|---|
| 2950 | 艙室層 | DepthRim |
| 3175 | 迷霧 | 原版 |
| **3177** | 外海層 | DepthRim |
| 3180 | 光照暗化（擷取畫面後套用夜色與燈光） | 原版 |
| **3250** | 己方 Pawn 提示（B2，比照原版剪影） | DepthRim / 原版剪影 |

己方提示必須排在光照暗化（3180）之後，否則在暗處會被一起壓暗而失去意義。

### 0.3 頂點色通道（所有階段完成後）

原版 `MapWorldUV.vert.glsl` 只傳位置與頂點色，所以所有逐頂點資料都塞在頂點色的四個通道裡。

| 通道 | 外海層 | 艙室層 |
|---|---|---|
| r | 靠近艙室的程度（現有） | 岸邊程度（現有） |
| g | **光照值**（B：四格平均；**含日光**，定義同原版 `GlowGrid.GroundGlowAt`，見 §D D9） | **光照值**（B：原本的開放水域旗標已不再使用；同一套定義） |
| b | 迷霧比例（現有） | 保留（目前固定 0） |
| a | 255（現有） | 水位（現有） |

若之後通道不夠用，再寫專用的頂點著色器（比照原版 `Transparent.vert.glsl` 帶 `inUv0`），把額外資料放進 uv。

### 0.4 參數命名

- 著色器 uniform 一律以 `_` 開頭，並寫 `// @default = ...` 註解（1.7 以這個註解決定材質沒設值時的預設值）。
- 原版全域值直接用同名 uniform：`_GameSeconds`（動畫時鐘）、`_RippleTex`（波紋貼圖）。
- 每個新參數都要同時出現在：著色器 uniform、`WaterVisualTierDef`（C 之後）、本文件的參數表。

### 0.5 每個階段的流程

1. 依本文件該階段的「步驟」實作。
2. 抽出純函式放進 `FloodingMath`，寫單元測試（`.source/DepthRim.Tests`）。
3. 建置：
   ```bash
   dotnet build .source/DepthRim/DepthRim.csproj -c Release
   ```
4. 單元測試（必須全過）：
   ```bash
   dotnet run --project .source/DepthRim.Tests/DepthRim.Tests.csproj -c Release -p:OutputPath=<暫存資料夾>/
   ```
5. 驗收測試：先只跑該階段新增的 id（`-Only`），通過後再跑完整套件，確認沒有退化。
6. 檢查 `Player.log`：不可有 DepthRim 相關的 ERROR，也不可有著色器編譯警告（「Could not load shader」）。
7. 看截圖，請使用者確認畫面。
8. 更新本文件的「狀態」欄、設計稿 §2.2、測試 README。

### 0.6 共用完成條件（每個階段都要滿足）

- [ ] 單元測試全過，新增的純函式都有測試。
- [ ] 完整驗收套件全過（偶發的遊戲啟動當機可重跑一次，見記憶 `depthrim-test-workflow`）。
- [ ] `Player.log` 沒有 DepthRim 的 ERROR、沒有著色器載入失敗。
- [ ] 迷霧格的頂點不帶任何地形、房間或光照資訊（V3 持續通過）。
- [ ] 截圖已給使用者確認。

## 階段 A：放大波紋、參數化

**狀態：** 已完成
**目標：** 波紋大到不干擾辨認水中細節；所有波紋相關數值改成材質參數。

### A.1 步驟

1. **外海層著色器**（`1.7/Shaders/DepthRim_WaterOuter.frag.glsl`）
   - 新增 uniform：`_RippleScale`（預設 0.03）、`_RippleSpeed`（預設 1.0）、`_RippleContrast`（預設 0.6）。
   - `ripple()` 的兩組取樣尺度改成 `_RippleScale` 和 `_RippleScale * 1.45`，漂移速度乘 `_RippleSpeed`。
   - 光紋帶寬跟著尺度放寬：`smoothstep(0.30, 0.42, h)` 改為以 `_RippleContrast` 混合後的較寬區間，避免放大後變成細線。
2. **艙室層著色器**（`DepthRim_WaterVolume.frag.glsl`）：同樣參數化，但 `_RippleScale` 預設 0.06（艙室面積小）。
3. **材質設定**（`SectionLayer_WaterOuter` / `SectionLayer_WaterVolume` 的靜態建構子）：明確設定上述參數，不依賴 `@default`，方便之後改成讀 Def（C 階段）。
4. **純函式**：把「波紋重複週期（格）= 1 / 尺度」寫成 `FloodingMath.RipplePeriodCells(scale)`，作為測試與文件的依據。

### A.2 參數初始值

| 參數 | 外海層 | 艙室層 | 說明 |
|---|---|---|---|
| `_RippleScale` | 0.03 | 0.06 | 波紋大約每 33 格／17 格重複一次 |
| `_RippleSpeed` | 1.0 | 1.0 | 漂移速度倍率 |
| `_RippleContrast` | 0.6 | 0.6 | 0 = 平滑起伏，1 = 現在的銳利光紋 |
| `_CausticStrength` | 0.22（不變） | 0.35（不變） | C 階段改成依層級 |

### A.3 完成指標

- 外海層波紋重複週期 ≥ 25 格，艙室層 ≥ 12 格。
- 近景截圖（鏡頭大小 9–14）中，Pawn、牆、物件的輪廓不會被光紋切斷。
- 兩個著色器新增的 uniform 都有 `@default`。

### A.4 測試

- **單元測試**：
  - `RipplePeriodCells` 的換算。
  - `ContentShaders` 擴充：檢查每個 `layout(...) uniform MaterialUniforms` 區塊裡的 `float`／`vec4` 欄位都有 `@default` 註解（`_GameSeconds` 等全域值除外）。
- **驗收測試**：V1、V2 現有截圖重拍，前後對照。不新增 id。

## 階段 B：光照控制可見度、潛水服頭燈

**狀態：** 已完成（頭燈改用 `GlowGrid.RegisterCustomGlower`，見 §D 偏離 D1）
**目標：** 有光的地方水清澈、沒光的地方混濁；穿潛水服的殖民者自帶一圈光。

### B.1 光照寫入頂點

1. 兩個 SectionLayer 的 `Regenerate` 裡，每個頂點取四格的 `map.glowGrid.VisualGlowAt(c)`，換算亮度：
   - `light = max(r, g, b) / 255`（和原版光照覆蓋層相同的來源）。
   - 界外的格子不計入；**迷霧格一律以 0 計入，且外海層的迷霧頂點直接寫 0**，不洩漏迷霧下有沒有光源。
2. 寫入頂點色 g 通道（見 §0.3）。艙室層把原本的「開放水域旗標」改為光照值，著色器裡讀 `vColor.g` 的地方一併改名。
3. `relevantChangeTypes` 兩層都加上 `MapMeshFlagDefOf.GroundGlow`。
4. **注意：** 原版 `GlowGrid.DirtyCell(cell)` 只標記光源所在的那一格，燈的照明半徑可能跨到相鄰區塊。驗收測試 V4 必須確認燈照範圍內、位於相鄰區塊的頂點也有更新；若沒有，改為在水位系統監聽 `map.events.Notify_GlowChanged` 或在燈具生成時以光照半徑標記周圍區塊。

### B.2 著色器：混濁度

1. 新增 uniform：`_ClearAlpha`（0.15）、`_MurkAlpha`（0.85）、`_LightMin`（0.05）、`_LightMax`（0.6）、`_LightTint`（0.25）。
2. 外海層（已探索部分）：
   ```glsl
   float light = vColor.g;
   float clarity = smoothstep(u._LightMin, u._LightMax, light);
   float alpha = mix(u._MurkAlpha, u._ClearAlpha, clarity);
   ```
   - 迷霧部分維持 `_FogAlpha`，不受光照影響。
   - `_LightTint`：亮處把水色往淺青色偏移一些，讓燈光看起來照進了水裡。
3. 艙室層：同樣公式，再乘以水位（水越少越透明）。
4. **純函式**：`FloodingMath.WaterAlpha(light, clearAlpha, murkAlpha, lightMin, lightMax)`，和著色器的公式一致。

### B.3 潛水服頭燈

原版 `CompGlower` 只在物件生成在地圖上時運作，穿在身上的衣物不會發光，所以要另外處理：

1. **做法（建議）：跟隨光源。** 新增一個看不見的物件 `DepthRim_SuitLampGlow`（只有 `CompGlower`，半徑 4.5，冷白光 `(200,225,255)`），由潛水服的 Comp 管理：
   - 穿著者在冰洋地圖上、而且在水中時，在穿著者所在格生成光源；穿著者移動到新的格子時才搬移（不是每 tick）。
   - 脫下、離開地圖、死亡、倒地超過設定時間時移除。
   - 存檔時不存光源本身，讀檔後由 Comp 重建。
2. **效能上限：** 每次搬移都會觸發光照重算。驗收時測 10 名穿潛水服的殖民者同時移動的情況（V4 的效能檢查）。若超出預算，改成每 N tick 才搬移，或是只在被選取／被徵召時開燈。
3. **替代做法（只在效能不行時考慮）：** 著色器端假光，把穿潛水服者的位置以 uniform 陣列傳給外海層，只讓附近的水變清澈。缺點：原版的夜色不會變亮，看起來比較假。

**實際做法（已實作，偏離見 §D D1）：** 不用隱藏的燈光 ThingDef，改用原版 1.7 的 `GlowGrid.RegisterCustomGlower`／`DeregisterCustomGlower`：

- `CompProperties_SuitLamp`（`glowRadius`/`glowColor`/`overlightRadius`/`downedOffTicks`）掛在 `DepthRim_DivingSuit` 的 `<comps>`。
- `CompSuitLamp.UpdateLamp()`：穿著者死、倒地超過 `downedOffTicks`、離開水、不在水下地圖、或所在格水位 ≤ 0.05 時關燈；已經亮著且在**同一格**就什麼都不做（不搬移、不重建）。
- `SuitLampUpdater.Update(map)` 由 `MapComponent_Flooding.MapComponentTick` 每 15 ticks 掃一次 `mapPawns.AllPawnsSpawned` 的 `apparel.WornApparel`，地面上的潛水服完全沒有開銷。
- `PostDeSpawn`（脫下、摧毀、離開地圖）與讀檔（`LoadSaveMode.PostLoadInit`）都會 `TurnOff()`；光源本身不存檔，讀檔後重新註冊。
- 原版第一個 handle 是 **0**，所以「有沒有光源」用 `CompSuitLamp.Lit` 判斷，不能用 handle == 0。

### B.4 參數初始值

| 參數 | 值 | 說明 |
|---|---|---|
| `_ClearAlpha` | 0.15 | 光照充足時的覆蓋程度 |
| `_MurkAlpha` | 0.85 | 完全沒光時的覆蓋程度 |
| `_LightMin` / `_LightMax` | 0.05 / 0.6 | 光照值低於下限視為全暗，高於上限視為全亮 |
| `_LightTint` | 0.25 | 亮處水色偏淺青的程度 |
| 頭燈半徑 | 4.5 格 | `CompProperties_Glower.glowRadius` |
| 頭燈顏色 | (200, 225, 255) | 冷白光 |

### B.5 完成指標

- 在開放水域放一盞燈：燈下頂點的光照值 ≥ 0.6，離燈 15 格外的頂點 ≤ 0.05。
- 燈關掉後，該區域重建，光照值回到 ≤ 0.05。
- 穿潛水服的殖民者所在格光照值 ≥ 0.5；脫下潛水服後光源移除、光照值恢復。
- 迷霧格頂點的光照值恆為 0（即使迷霧下放了燈）。
- **效能：** 單一外海層區塊重建 ≤ 2 ms；10 名穿潛水服的殖民者同時移動時，每秒的區塊重建總時間 ≤ 10 ms。

### B.6 測試

- **單元測試**：`WaterAlpha` 的單調性（光越亮越透明）、上下限、`_LightMin = _LightMax` 時不除以零。
- **驗收測試 V4（新增）**：
  1. 在開放水域放一盞立燈並接電：檢查燈下與遠處的頂點光照值、開關燈後重建。
  2. 檢查燈照範圍跨到相鄰區塊時，相鄰區塊也有更新（§B.1 第 4 點）。
  3. 在迷霧格下放一盞燈：外海層該處頂點的光照值仍為 0。
  4. 殖民者穿潛水服進入水中：光源生成、移動後跟隨、脫下後移除。
  5. 效能：用 `Stopwatch` 量測重建時間，寫進記錄（note），超過上限則失敗。
  6. 截圖：燈的周圍、穿潛水服的殖民者近景。

## 階段 B2：暗處的己方 Pawn 提示

**狀態：** 已完成
**目標：** 己方 Pawn 在混濁的水裡仍看得到淡淡的輪廓；敵人與野生生物沒有提示。

### B2.1 步驟

1. **判斷誰要提示**：`pawn.Faction == Faction.OfPlayer`（含己方動物、機械體），已生成、在水下地圖、不在密閉艙室（`IsOpenAt`），而且所在格的混濁度 ≥ 門檻。
2. **混濁度來源**：用和著色器相同的 `FloodingMath.WaterAlpha`，以該格的光照值計算，確保畫面與判斷一致。
3. **繪製**：
   - 新增 `MapComponent` 的 `MapComponentUpdate`（主執行緒）：只對畫面內的己方 Pawn 畫剪影。
   - 圖形用 `pawn.Drawer.renderer.SilhouetteGraphic`，材質用原版剪影著色器（`ShaderDatabase.Silhouette`，繪製順序 3250，在光照暗化之後）。
   - 顏色：淡青色，`alpha = (混濁度 - 門檻) / (1 - 門檻) × 0.6`，所以在亮處完全不畫，越暗越明顯。
   - 不使用原版 `SilhouetteUtility.DrawGraphicSilhouette`：它受玩家的「醒目提示樣式」設定控制，我們的提示必須永遠有效。
4. **開關**：跟著右下角的水體顯示開關；關掉水體時也不畫提示。

### B2.2 參數初始值

| 參數 | 值 |
|---|---|
| 提示門檻（混濁度） | 0.5 |
| 最大不透明度 | 0.6 |
| 顏色 | (120, 220, 255) |

### B2.3 完成指標

- 暗處的己方殖民者有提示；同一位置的敵方 Pawn 沒有。
- 亮處（燈下或穿潛水服、混濁度 < 門檻）沒有提示。
- 密閉艙室裡的 Pawn 沒有提示（艙室層不蓋住 Pawn）。
- 畫面內 30 名己方 Pawn 時，提示繪製每幀 ≤ 0.5 ms。

### B2.4 測試

- **單元測試**：提示 alpha 的換算（門檻以下為 0、單調遞增、上限）。
- **驗收測試 V5（新增）**：在暗處放一名己方殖民者與一名敵方 Pawn，檢查「要不要提示」的判斷；開燈後判斷改變；截圖對照。

## 階段 C：層級設定與淺海效果

**狀態：** 已完成
**目標：** 每個水深層級一組參數，存在 XML；冰洋基地使用淺海參數，並加上淺海專屬效果。

### C.1 `WaterVisualTierDef`

新增 `Defs/Rendering/WaterVisualTiers.xml`，每個層級一個 Def：

| 欄位 | 型別 | 用途 |
|---|---|---|
| `tier` | `DepthTier` | 對應的層級（唯一） |
| `waterColor` / `deepColor` / `fogColor` | Color | 已探索水色、深處水色、迷霧區水色 |
| `clearAlpha` / `murkAlpha` | float | B 階段的混濁度上下限 |
| `ambientReach` | float | 日光能穿多深（0–1）：淺海 1 = 有日光就算有光；越深越小（見 §D D9） |
| `rippleScale` / `rippleStrength` / `causticStrength` | float | 波紋尺度與強度；`rippleStrength = 0` 時著色器跳過波紋 |
| `lightShaftStrength` | float | 淺海光柱強度（其他層級 0） |
| `snowDensity` / `snowSpeed` | float | 海洋雪（D 階段） |
| `biolumDensity` / `biolumColor` | float / Color | 生物光（D 階段） |
| `hazeStrength` | float | 海床沉積霧氣（D 階段） |
| `wobbleStrength` | float | 變溫層假扭曲（D 階段） |
| `compartmentEffects` | bool | 艙室層是否套用 D 階段效果（預設 false，見 E） |

- `ConfigErrors`：四個層級都必須各有一個 Def、不可重複；數值必須在 0–1（尺度除外）。
- 新增 `DepthRimDefOf` 不需要逐一列出；用 `WaterVisualTierDef.For(DepthTier)` 靜態查表。

### C.2 每層級材質

1. 外海層與艙室層各建一個 `Material[4]`（依層級），在第一次用到時建立（主執行緒，`Regenerate` 本來就在主執行緒）。
2. `Regenerate` 依 `FloodingUtility.DepthTierOf(map)` 選材質。地圖的層級改變時（例如潛艇下潛），呼叫 `map.mapDrawer.WholeMapChanged(DepthRim_Water)` 整張重建。
3. 材質參數從 Def 讀取，Def 重新載入時（開發中）可用除錯動作重建材質。

### C.3 開發用的層級切換

潛艇還沒做出來之前，冰洋基地永遠是淺海。為了調整其他層級的畫面：

- 新增除錯動作「DepthRim: Override water visual tier」，選擇層級後寫入 `MapComponent_Flooding.debugTierOverride`（不存檔），並整張重建。
- `FloodingUtility.DepthTierOf` 只在**渲染**時讀這個覆寫；水壓、滲水速度等遊戲數值不受影響（照明只影響畫面的決定）。

### C.4 淺海效果

1. **大尺度波紋反射**：A 階段的波紋，`rippleStrength` 0.8。
2. **穿過冰層的光紋**：A 階段的光紋，`causticStrength` 0.3。

## 階段 D：海中央與海床效果

**狀態：** 已完成
**目標：** 變溫層、深海、海床各有辨識度高的氛圍，全部在著色器裡程序化產生。

### D.1 著色器結構

- 外海層著色器加上四個效果函式，各自由參數控制，參數為 0 時以 `if` 跳過：
  - `marineSnow(world, t)`：多層網格雜訊產生的小亮點，緩慢往下（螢幕的 -z 方向）飄，配上輕微的左右擺動。
  - `bioluminescence(world, t)`：稀疏的冷色光點，各自以不同相位緩慢明滅；只在混濁度高（暗處）時明顯。
  - `sedimentHaze(world, t)`：低頻雜訊產生的貼地霧氣，提高 alpha、把顏色往 `deepColor` 拉。
  - `thermoclineWobble(world, t)`：沿一個方向的正弦帶，偏移波紋取樣座標與顏色，產生「水在晃」的錯覺（不擷取畫面）。

| 效果 | 亮處 | 暗處 |

| 海洋雪 | 清楚可見（被燈照亮的懸浮物） | 幾乎看不到 |
| 生物光 | 被燈光蓋過，幾乎看不到 | 明顯 |
| 沉積霧氣 | 變淡 | 濃 |
| 變溫層晃動 | 不受影響 | 不受影響 |

## 附錄 D：與本指南的偏離、以及刻意留下的後續工作

### D1 潛水服頭燈不用隱藏光源 ThingDef（B.3）

- **指南寫的**：新增看不見的 `DepthRim_SuitLampGlow`（只有 `CompGlower`），由 Comp 生成／搬移／移除。
- **實際做法**：`GlowGrid.RegisterCustomGlower(IntVec3, float, ColorInt, float, bool)` ＋ `DeregisterCustomGlower(int)`。
- **理由**：行為完全相同（`VisualGlowAt` 讀的是同一個累積光照），但不必生成／銷毀 Thing、不必存檔、不必擔心光源被其他系統（存檔、地圖卸載、搬運）弄丟。搬移仍然是「換格才搬」，成本是兩次 handle 操作。
- **注意**：原版第一個 handle 是 0，所以狀態用 `bool Lit`，不能用 `handle == 0` 當哨兵。

### D2 每層級材質用 `new Material(shader)`，不是 `MaterialPool`

- **理由**：`MaterialPool.MatFrom` 以 `MaterialRequest` 為 key 共用材質，無法為同一著色器準備「8 份參數不同」的材質；`MaterialAllocator` 在 1.7 是 `internal`，模組不能呼叫。
- **結果**：`WaterTierMaterials` 為每個層級各建一份外海層與艙室層材質（共 8 份），第一次用到時在主執行緒建立，之後所有區塊共用。除錯動作「Reset water materials」會丟掉參考並照 Def 重建。

### D3 `compartmentEffects` 只存在、沒有分支（E）

- Def 有這個欄位、四個層級都是 `false`，`WaterTierMaterials.Volume` 也完全沒有把 D 階段的效果接上去（艙室層著色器裡根本沒有海洋雪／生物光／霧氣／晃動的函式）。
- **後續**：若之後要讓某些層級的艙室也有懸浮物，要先在 `DepthRim_WaterVolume.frag.glsl` 補上對應的 uniform 與函式，再把 `compartmentEffects` 接進 `CreateVolume`。

### D4 艙室層的波紋尺度跟著 Def 走（A.2 → E.1）

- A.2 的「艙室層 `_RippleScale` 0.06」是 C 階段之前的值；E.1 規定艙室層改讀 Def 的 `rippleScale`（0.03），所以現在兩層的波紋週期一致（33 格），仍然滿足 A.3 的「艙室層 ≥ 12 格」。
- 如果看截圖覺得小房間裡的波紋太平，就把 `WaterVisualTierDef` 加一個 `compartmentRippleScale`（預設 0.06），或在 `CreateVolume` 乘一個倍率。

### D5 V7 的 FPS 比較是「有雜訊的量測」

- V7 會把四個層級的 FPS 寫進 note，並檢查深海不低於淺海的 80%（明顯退化）與 90%（指南 D.3 的目標）。驗收執行時遊戲是無 vsync＋Ultrafast 模擬，幀率本身有 ±20% 的雜訊，所以 90% 那條是**參考值**；真正的 D.3 結論要看 note 裡的原始數字與人工確認。

### D6 測試期間的頭燈不會被 `LevelAt` 卡住

- 頭燈條件是「所在格水位 > 0.05」，開放水域固定 1、艙室抽乾後為 0；所以乾艙室裡穿潛水服不會亮燈（設計如此：艙室本來就看得到）。

### D7 `glowRadius` 的有效照明比它宣稱的少一格（B.1、B.3 的量測前提）

- `Verse.Glow.ComputeGlowGridsJob.SetGlowFromDist` 的實際公式是
  `強度 = Lerp(1 - d/R, 1/d², 0.4)`，其中 `d = intDist / 100`，而 **`d` 從光源自己的格子就是 1**（中心格 `intDist = 100`，每走一格 +100，斜走 +141）。
- 所以立燈（`glowRadius` 12、`glowColor` 214,148,94）的實測值是：燈下 `0.95 → 203/255 = 0.796`、10 格 `0.053 → 11`、**11 格 `0.0028 → 0`**。也就是說「半徑 12」的光圈只有大約 10 格看得到東西。
- 這直接影響兩件事：
  1. B.3 的潛水服頭燈用 `glowRadius 4.5`，實際可讀的照明只有 3～4 格，符合原本「只夠看清身邊」的設計；若要更遠就得加大 `glowRadius`，而不是調顏色。
  2. 驗收 V4 的「燈光跨越區塊邊界」不能用「11 格外的鄰區格子」來量（那裡恆為 0）。現在的做法是把立燈放在**離區塊邊界 3 格**的位置，再量鄰區第 3 格，讀值約 0.41。
- 頭燈（`glowRadius` 4.5、顏色 200,225,255）的實測值也對得起來：腳下 `0.867`（`d = 1`）、**斜一格 `0.345`**（`d = 1 + 1.41 = 2.41`）。
  驗收時看到 `0.345` 就代表「光源還在上一格」——`pawn` 會在兩次掃描（15 ticks）之間走動，而光照格是每幀才算的，
  所以量測要拿 `CompSuitLamp.RegisteredCell`（真正註冊的格子）當探針，不能拿 `pawn.Position`。

### D8 換層級時區塊會留下空的舊 submesh（C.6、E.1 的量測前提）

- `SectionLayer.ClearSubMeshes` 只把頂點清空，**不會**把 submesh 從清單移除；而 `GetSubMesh(material)` 是「同材質就重用、不同材質就新增」。所以一個區塊切換過 N 個層級之後，`subMeshes` 裡會有 N 份，只有最後一份有頂點，其餘是空殼（不影響畫面，只是每區塊多幾個空 mesh）。
- 因此驗收測試讀「這個區塊用哪份材質」時**不能**用 `subMeshes.FirstOrDefault()`——那會拿到最舊的空殼，材質還是淺海的。要用「第一個有頂點的 submesh」，也就是 `Tests_Visual.LiveMesh`。
- V6／V8 從前的假失敗正是這件事：水色永遠讀到淺海的 `(0.06, 0.24, 0.40)`，而 `_RippleScale` 卻對得起來——因為四個層級的波紋尺度都是 0.03，那個檢查其實沒有鑑別力。

### D9 「光照」改成原版的定義：含日光，並由層級決定日光能穿多深（B、C）

- **原本的寫法**：`FloodingMath.LightOf(map.glowGrid.VisualGlowAt(c))` 只取**人造光**（註冊的 glower／自訂光源），
  不含日光。結果：白天淺海到處都是「沒光」→ 吃到 `murkAlpha 0.85`，整片看起來又濁又不透明。
- **現在**：`FloodingMath.CombineLight` = **日光與人造光取大者**。
  - 日光（**照抄**原版 `Verse.GlowGrid.GroundGlowAt` 的取法）：無屋頂時 = `map.skyManager.CurSkyGlow`，
    所以白天開放水域一定「有光」，和左下角顯示的「光度」是同一個數字。
  - 人造光（**刻意不照抄**）：用 `LightOf(VisualGlowAt)` 的原始 0–1 平滑衰減。原版 `GroundGlowAt` 給遊戲判定用的是
    「×3.6、上限 0.5」，套到著色器上會把燈光壓成一片 0.5 的**硬邊圓盤**，
    B 階段調好的「燈下 0.796 → 3 格外 0.353 → 10 格外 0」漸層就消失了。
- **新增 `ambientReach`（每個層級）**：日光要乘上它，預設淺海 1.0、斜溫層 0.55、深海 0.25、海床 0.12。
  沒有這個折減，深海在白天也會「因為有日光」而變透明，D 階段的效果就全沒了。人造光不折減——燈就掛在水裡。
- **連帶影響**：白天開放水域不再是「暗水」，所以
  1. 暗處提示（B2）在白天淺海不會出現（設計如此），V5 因此固定用 `DepthTier.Seabed` 來測；
  2. V4 的「暗」改成相對於日光基準（`Ambient(map) = CurSkyGlow × ambientReach`）而不是絕對 0；
     而且白天淺海的日光就是 1.0，燈的貢獻完全被蓋掉、量不出來，所以 V4 也固定用 `DepthTier.Seabed` 當背景。
- 取值包裝在 `WaterLight.At(map, cell, ambientReach)`；`FloodingMath` 仍然不碰地圖，公式本體是純函式、有單元測試。

### D10 海洋雪改成兩層視差＋每顆自己的擺動（D）

- **原本的寫法**：整個場只平移 `-t * 0.30 * _SnowSpeed` 一個量，所以所有雪點**同步**往下掉，看起來像整片在滑動；0.30 格／秒也偏快。
- **現在**：`marineSnowLayer` 讓每顆雪自己的擺幅、擺動頻率、相位、上下浮沉、大小、亮度都來自自己的 hash，
  `marineSnow` 再疊兩層不同速度（1.0× 與 0.42×，慢的那層看起來更遠）拉出視差；基礎速度由 0.30 降到 **0.085 格／秒**。
- `snowSpeed`（Def）仍然是倍率，想更慢／更快改 Def 就好，不必重編譯著色器。

### D11 白天「全都有光」之後，`clearAlpha` 必須調高（B、C）

- 日光算光之後，**整片白天開放水域都會落在「清澈」端**，於是 `_ClearAlpha` 從「燈照到的那一小塊」變成「整張地圖的常態」。
- 原本淺海 `clearAlpha 0.15`（B 階段為燈池調的「水幾乎透明」）放到整片海洋上就不成立：
  水只剩 15% 存在感，海底的暗色岩盤直接透上來，看起來像「一塊暗色玻璃」而不是水。
  驗收截圖（已探索的淺海、日光 1.0）可以清楚看到這個問題。
- 所以四個層級的 `clearAlpha` 調成 **0.40 / 0.45 / 0.50 / 0.50**（`murkAlpha` 不變 0.85–0.93）：
  日光下仍看得到海底，但水本身有顏色與波紋；暗處依然幾乎不透明，兩端差距仍在。
- 這是**純 Def 值**，覺得太淡或太濃改 `1.7/Defs/Rendering/WaterVisualTiers.xml` 就好，不必重編譯、不必重啟著色器。

### D12 深淵沒有「亮環」，判準改用實測的兩個比值（P2-10）

深淵地板（二期）第一次做出來時，我原本想用「崖邊峰值 ≥ 60/255 且峰值／核心 ≥ 10×」當驗收門檻。實測後**放棄那個門檻**：隔著一層水看崖壁，10× 在物理上不可能，那個數字是我憑感覺訂的。

實測（1920×991 截圖、視窗由 V9 自己印出的螢幕座標決定，1 格 ≈ 12.4 px）：

| 視窗 | 中位數亮度 |
|---|---|
| 核心（中心 ±3 格） | 23.7 |
| 西側崖邊帶（燈那一側，1 格寬） | 43.8 |
| 東側崖邊帶（沒有燈） | 16.0 |
| 深淵矩形內部（去掉 1 格邊） | 23.3 |
| 矩形外被照亮的水面 | 46.0 |

- **成立**：深淵內部 / 周圍水面 = **0.51×**（洞口真的比周圍暗一半，這就是「深淵吸光」）；
  崖邊 / 核心 = **1.85×**（有「靠崖看得到崖壁往下延伸」的過渡）。
- **不成立**：崖邊 43.8 ≈ 周圍 46.0，所以沒有「比周圍亮一圈的光環」。原因是**外海層照常蓋在深淵上**
  （計畫 §2.7.4 的規定），崖邊反光被水層壓到與周圍同級；單燈也只照亮西側，東側是 16.0。
- **決定（2026-11-01，使用者確認）**：接受「暗洞＋柔邊」，不改水層、不改 `_RimColor` 係數（維持 1.2）。
  若之後真的要亮環，選項是「深淵格降水的透明度」或「RimCells 4 → 6 加寬亮帶」，兩者都會動到計畫的措辭，要先談。
- 驗收對應：V9 的 18 條檢查只驗**資料**（`rim 255 vs centre 0`、`rim 光照 128 vs centre 55`、`centre < rim/2`、
  著色器 `DepthRim_Abyss ≠ Cutout`、121 格、水位 1.000、`!Standable`、四類錯誤字串 0）；
  **像素比值不進自動測試**，因為那需要外部讀 PNG。V9 會印出 `abyss rect x…y…; rim (…); centre (…)`，
  讓外部量測用同一組視窗做前後對比。
